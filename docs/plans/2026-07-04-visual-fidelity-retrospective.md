# 视觉保真度偏差复盘

日期：2026-07-04

## 背景

我们有设计系统 SSOT（`designs/agentdeck-design-system/`）和一整套工程门禁（AGENTS.md 边界、N1–N8 不变量、`cargo test`/`swift test`、SDD/TDD/双审流程），但最终 macOS 界面与目标设计稿（图1）偏差很大：用户气泡多了「You」标题和橙色边条、右侧环境面板是「本地/master/提交或推送/来源」占位骨架而非只读「Changes/Git」卡、还有一个把用户气泡撑满全高的运行时布局 bug。本文记录为什么会这样，作为整改依据。

## 一句话结论

**门禁强在能被机器检查的层面（协议、架构、行为、颜色 token），弱在需要人眼看图判断的层面（组件构成、视觉保真）。** 而在一个「必须连 daemon 才能看到内容」的应用里，人工目视 QA 几乎从不发生。设计系统给了词汇（token），没给契约（组件保真 + 视觉回归）。

## 根因

1. **SSOT 锁的是 token，不是构成。** `tokens.json → build.mjs → DesignTokens.swift` 只生成颜色/间距/圆角/字体，且禁止手改——所以颜色是忠实的。但 `COMPONENTS.md` 的组件规格是给 Web 的 CSS 类描述，与 AppKit 实现无任何绑定。每个 AppKit 组件是一次手工再解释，token 拦不住「加了个设计里没有的标签」。

2. **叫「快照测试」的东西不快照。** `RenderSnapshotTests` 把 PNG 渲染到 `/tmp` 后从不比对，只验证「不崩」；且固定在 900pt 宽度渲染，结构性地绕开了巨型气泡 bug 的触发条件（真实 `NSTableView` 初始列宽极小）。零视觉回归门禁 + 假的安心感。

3. **设计参照漂移，代码追的是另一张。** `2026-07-01-codex-desktop-chrome-sync` 同步的是「当时的 Codex Desktop」（参照 A），目标 mockup 是图1（参照 B）。没人回头拿图1 重新 diff。环境面板那份 sync 文档本身就标注了「静态占位」，占位当成品交付。

4. **换框架天然掉保真度。** SwiftUI→AppKit（`83e8853`）逐视图手工重写。移植默认保真、从不验证保真：有东西被丢（`loadHistoryOnAppear`），有东西被重新诠释（气泡）。AppKit 命令式 Auto Layout 还引入了 SwiftUI 里不存在的一类运行时布局 bug（宽度时序、窗口自撑大），而没有测试看渲染布局。

5. **本地目视 QA 结构性地难，所以基本没发生。** 真实 app 要 daemon + vendor CLI + 登录才能显示内容，「跑起来看一眼」成本高——偏差恰在最难看的地方积累最快。（这正是本次临时搭的预览台补上的缺口：它一上来就照出了巨型气泡和 hash 警告。）

6. **流程门禁为「对不对」优化，不为「像不像」。** SDD/双审在正确性/架构/测试上很强，审查提示词聚焦 spec 合规与代码质量；但「像不像设计」从不是一道门——没有审查者手里拿着 mockup，没有测试把它编码进去。守的 N1–N8 是架构不变量，不是视觉不变量。

## 教训

我们为「能自动化的失败模式」（协议漂移、vendor 分支泄漏、行为回归）建了门禁，把唯一需要一张图的失败模式（视觉保真）留给了非正式人工注意力。要堵住它，必须把「视觉保真」也变成一道能自动跑、且有人拿着 mockup 比对的门禁。
